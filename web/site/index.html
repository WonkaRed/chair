Where these lines come from

Each is the last sentence of a set of minutes the Chair signed on the current token, token.chair-coin-3.testnet. The AI model writes that sentence itself, in a second call, and a filter checks it before the Chair signs; if it fails the filter, a fixed line closes the minutes instead and is not shown here. These four are recorded meetings. Once the page has read the chain, the newest four closing sentences replace them, each checked against the hash the contract logged. Each links to its transaction, which holds the full text.

How the check works, and what it does not show
  • The contract stores the hash and logs it in a policy_set event with the meeting number and the rate. The chair also sends the reasoning text as an extra argument of the same set_policy call. The contract ignores it, but it stays in the transaction, so it is public.
  • This page reads that text from the transaction's arguments. Decisions made before the chair sent it have no text there: for those, the chair's own saved text is used, copied into this page's files when the page is built, from the docs/ folder of the repo. Nothing is fetched from a model or a server of mine.
  • Your browser computes the SHA-256 of the exact text shown and compares it with the hash read from the chain. Verified means the text matches that hash. A text read from the transaction sits in the same transaction as the hash, so it cannot be quietly rewritten afterwards. A decision with neither text shows its hash only.
  • A match does not show the chair was right, that the text is the real reason for the rate, or that an AI wrote it: the contract stores only a hash the chair supplies. It shows the text was not edited after the decision.

What this page does not prove
  • It does not say the chair is wise. The contract bounds the chair; it does not make it right.
  • It does not say a bad Chair cannot do harm. A Chair that prints at its ceiling keeps doing so for as long as the holders let it. What stops it is the holders; see "How bad could a rogue Chair get?".
  • It does not say anything about price, liquidity or returns. The simulation is a model of supply under stated assumptions.
  • The refusals listed under "Times the contract told the Chair no" include deliberate test calls that I made to show the bounds hold; each is labelled in its row.
  • The one time holders replaced the Chair on the testnet, at meeting 10, it was my own scripted test accounts voting, not a crowd. It shows the mechanism works, not that anyone is using it.
  • The faucet gives out at most 10,000 coins in total (200 visitors x 50), about 1% of the coins that exist, on purpose: visitors can never vote the Chair out, which takes over 5%. These are test coins from a pool I control, with no value.
  • The log comes from an index, so it is checked, not signed: its sums must equal the chain's own ledger, and a difference is shown as such. Each row links to its transaction so you can check any entry by hand.
