# web

The public page for $CHAIR, written first for someone who has never heard of crypto and then, as you scroll, for people who check. The top says in one plain sentence what the AI is doing to the supply right now (built from the chain's rate and limit, never from the Chair's text), with two actions: "Make the Chair overreach" and "Ask the Chair a question". Right under the hero is one line of the Chair's (the newest press answer on chain, with a real fixed fallback until it is read), then come the overreach game, the press conference, the best-of lines, "What holders control" (the staked share, the seated Chair, any challengers against the impeachment bar, and the impeachment that already happened, from `get_policy`, `get_supply`, `get_params` and `get_candidates`; `js/holders.js`), the Chair's decisions (a plain line from each decision's numbers, then "In the Chair's words", checked against the hash on chain), the times the contract told the Chair no, the live numbers with one chart, and below them, folded: the ledger of every mint and burn checked against the token's own ledger, the worst case stated from the contract's numbers (`js/bound.js`: at most about 2.02% a day even held at the limit, a week, 30 days, the time to the supply limit; and the three restraints) above a 60-epoch simulation of what the contract's rules do under five behaviours of the chair, the guarantees with their proofs, and what the page does not prove. Static files: plain ES modules,
no framework, no backend, no external fonts or scripts. Sections ease in on scroll (`js/reveal.js`) only when script and `IntersectionObserver` exist and reduced motion is not asked for; otherwise everything is simply there. It works from `make serve` and from any static host.

## Build, serve, test

Needs Node 22.22.2 or newer and npm (the build compiles `../sim` first).

```sh
make -C web build    # compiles ../sim, writes web/dist (site + config + fixture + the reasoning bundle + a verbatim copy of the compiled simulator + the CSP)
make -C web serve    # builds, then serves web/dist at http://127.0.0.1:8080/ (`PORT=8081 make -C web serve` to change it; a busy port is reported with that hint)
make -C web test     # builds, then `node --test "test/*.test.mjs"`: 247 tests, no browser, no network
```

Deploying is copying `web/dist` to any static host.

## Config: `config.js`

The one file to edit after deployment: `account` (the token account; shipped pointing at the live testnet token `token.chair-coin-3.testnet`, see `docs/testnet-deployment.json`),
`rpcUrls` (NEAR JSON-RPC endpoints in order of preference, the source of truth for every total; see Throttled or down RPC), `indexerUrl` (FastNEAR transactions API, the source of the event list),
`explorerUrl`, `repoUrl`/`repoRef` (spec and test links), `pressDiscoveryUrl` (where the page finds the press desk; see Press conference), and `fixture`. `fixture: null` (as shipped) reads the live chain; setting it to a path, as the tests do, shows
`fixtures/sandbox-run.json` instead and says, in a banner, "recorded sandbox run, not a live chain". The build writes the page's
Content-Security-Policy from this file: `connect-src` allows `'self'` and, only when `fixture` is `null`, exactly the origins of every `rpcUrls` entry and
`indexerUrl` (https only), plus, only when `pressDiscoveryUrl` is set, that document's origin (https; any other scheme fails the build) and `https://*.trycloudflare.com`, where the press desk lives. Scripts and styles are `'self'` only; the page has no inline script or style.

## Throttled or down RPC

The page reads the chain from the visitor's browser, so a public RPC that throttles would break it for that visitor. `rpcUrls` in `config.js` is an ordered list (shipped: `rpc.testnet.fastnear.com`, `near-testnet.drpc.org`, `rpc.testnet.near.org`, ordered by fewest 429s in a 30-call probe on 2026-11-11; every one answers `query` with `call_function` and `view_access_key_list` and sends CORS headers). One transport in `site/js/sources.js` serves every call:

- A network error (a rejected fetch, which is also what a browser reports for a 429 whose response has no CORS header, as FastNEAR's has), a timeout (10 s), HTTP 429, any other HTTP error, or a body that is not JSON moves the call to the next endpoint at once.
- The endpoint that last answered is where the next call starts. After a whole failed round the call pauses 400 ms and makes one more round, then fails once.
- A JSON-RPC error (`UNKNOWN_BLOCK`, a contract panic) is the node's real answer: no failover.
- The footer's "Views come from" names the endpoint that last answered (all candidates until one has).
- The transactions index (`indexerUrl`) has no second public instance with the same API, so it keeps one endpoint, tried twice with one 400 ms pause between (a hung index costs the same 10 s timeout per try as before). FastNEAR's index does throttle per address (measured 2026-11-12: a 429 with no CORS header, which the browser reports as a network error, after about 100 requests in a few minutes from one address; a probe 20 s after a 429 was answered normally). A cold load reads the hash list (pages of at most 200) and the transactions in batches of 20 (the index's own limits), so a handful of reloads could reach it. `js/txcache.js` therefore keeps every *complete* transaction in `localStorage` under `chair-txs/1:<token>`: complete means every receipt id that its outcomes list (the transaction's own, then each receipt's, refunds included) has an outcome in the reply, so nothing still running is kept and no clock is involved. Entries are reduced to the fields the page reads (about a quarter of the size, 1 KB each, other contracts' receipts dropped, positions kept), capped at 1,500,000 characters (the oldest are left out first). A reload asks the index for the hash list and only the transactions it has not kept, and batches that arrived before a failure are saved. What was kept is not trusted forever: when a load's log does not reconcile with the chain (status mismatch) or the newest decision read is older than the chain's `last_set_epoch`, and the load drew on the saved copy, it is cleared so the next load reads everything afresh. Storage is optional: missing, blocked, full, corrupt or oversized, it reads as empty and the page behaves the same. When it stays down only the log degrades: the chain's totals stay, the status reads "Log incomplete" with a Try again button.
- If every RPC endpoint is down on first load the page shows "The chain could not be read" and no numbers. If it fails during a Try again, after data was already on screen, the data stays and a quiet "Reconnecting" note is added above the log status.

To add or reorder an endpoint, edit `rpcUrls` only: the build puts each host in the CSP.

## How the log works, and how it fails

1. Views (`get_params`, `get_policy`, `get_supply`, access keys) come from the RPC. Those totals are shown even when the index is down.
2. The indexer lists the transactions that touched the token, and each transaction's receipts and logs are read. NEP-297 events
   (`ft_mint`/`ft_burn` with the contract's memos, and the `chair` standard's `epoch_minted`/`transfer_burned`) become log rows with epoch,
   amount, reason and a transaction link. Anything it cannot parse is listed as an anomaly, not dropped.
3. Event sums are compared for exact equality with `get_supply` (launch, minted, burned), **at the block of the last transaction that logged an event**:
   views project a mint that is due but not yet applied, and no event exists for it until the next transaction, so the page shows that separately as "due".
   The identity `total = launch + minted - burned` is checked in the page on the chain's own numbers.
4. Statuses: *complete* (sums equal), *mismatch* (they differ: "the log is not complete"), *incomplete* (the index failed or ended early: no event total is claimed,
   and a retry button is shown when trying again may help), *unverified* (the RPC node no longer has the block needed to pin the comparison). An RPC failure shows no numbers at all.

Chain strings are text only (`textContent`, never markup). Control, bidi and invisible characters are shown as `\u{...}`, and an account id that is not a valid NEAR id is shown as invalid.

## Chair minutes

**The hero** shows the Chair's latest decision as a large pull-quote (the minutes are written in plain words by the agent now, so when the text has no "basis points", "bps" or "epoch" in it the page adds no line of its own; for older texts that do, it adds one plain line built from the numbers, above "In the Chair's words"). It shows the prose of the reasoning text (without the boilerplate header lines), the meeting number ("Meeting N"; the title says epoch), the rate as a percent with the basis points as a small tag and "Before: ...",  and a "Verified on NEAR testnet" mark that opens to the hash, the transaction link and how the check works (or says plainly that the check failed or could not run). **The Chair minutes** section below lists the earlier decisions, newest first, 3 at first and 20 more per press of "Show more". Each card leads with the prose; an older text that still speaks in basis points and epochs gets a one-line plain translation built from its numbers above it ("Kept the rate at +0.15%. That prints 0.15% more coins a day for holders who staked."); the repeated header lines ("$CHAIR decision, epoch N, chair ..." and "Rate in effect ... bps; decision ... bps") are shown as small metadata, and the hash, the transaction and who decided are behind "Proof and details". From the voice change on, the reasoning is written in character ("The Chair", a deadpan parody of a central banker); older decisions keep their plain text, and the page shows either exactly as hashed. When the chair has been silent the section says for how many epochs and what the rate has decayed to.

**First paint.** The four quick views (`get_params`, `get_policy`, `get_supply`, `get_candidates`) are read first, in parallel, and `loadLog` hands them to the page (`onViews`) before it reads the slow transaction index: the plain sentence, "What holders control" and the worst-case section fill in about a second, the minutes and the chair's newest line when the index has been read. Until then the hero holds its size with grey placeholder bars (one screen-reader announcement, no duplicate text), and if the index cannot be read the hero's box is never empty: it shows the newest decision this browser saved, titled "Saved minutes" (never "Latest"), with a neutral "Matches the saved hash" badge instead of the verified tick (its fold-out says text and hash both came from this browser's saved copy, not from the chain on this load), with its meeting number and a line saying it comes from the saved copy and whether the chain agrees it is the last (the chain's `last_set_epoch`); with nothing saved it says, from the chain's own views, the rate in force, the meeting and the Chair's account. A failing `get_candidates` shows "could not be read" for the challengers only.

**Read-ahead.** The index is paged newest first (`desc`, reversed to oldest first, so the rest of the page sees the same list as before). As soon as the first page arrives, `sources.js` `peek` fetches the newest 20 hashes in one request, keeps the complete ones (`ahead`; the full read asks for no hash twice and writes them into the saved copy), and `loadLog` decodes the newest decision from them and offers it as `onLatest`, so the hero minutes card is drawn from that one response instead of after the whole log. It is offered only when its meeting is not behind the chain's `last_set_epoch`, never after `loadLog` has returned, and a failed read-ahead changes nothing (the full read goes on as before). The full read redraws the card only if the newest decision differs, so an opened proof fold is not shut. The Chair's agent log has a `supply_epoch` field, but it is not on chain or in the index, so the page cannot use it: the staked share under "What holders control" is labelled "now, at meeting N" and the Chair's own text carries the share of its own meeting.

**On a phone** (40rem and narrower) the deep parts are native `<details class="phone-fold">`: the minutes list, the times the contract said no, the live numbers, the simulation, the guarantees, and the challenger list with the past replacement. They are open in the HTML (nothing is hidden without script) and `js/phonefold.js` shuts them on a phone and opens them again when the screen grows; on a wide screen their summary is hidden by the stylesheet. A link to a section opens its phone fold. All content stays in the page.

**The overreach panel** frames the press as the worst case the contract is built for: the visitor takes the Chair's own signing key and makes it ask for a rate beyond the limit. The result leads with the stamp, a plain verdict and a link to the transaction; the raw RPC `curl` is behind a "Check it yourself" fold. One calm line says the model did not choose the number.

- **From the chain:** every `policy_set` event (`epoch`, `rate_bps`, `previous_rate_bps`, `reasoning_hash`, the chair account) in the same transactions the log reads (`js/decisions.js`), so the feed is live and shares the log's trust rules.
- **From the transaction:** the live agent sends the reasoning text as an extra `reasoning` argument of its `set_policy` call, which the contract ignores. The page reads it from the transaction's arguments (`argsOf` and `chainText` in `js/decisions.js`), keyed by transaction, and checks it against the hash in that transaction's own event, so a text that does not belong to its transaction is shown as a mismatch, never hidden. Arguments that are not a text (another method, bad base64 or UTF-8, a non-string or empty `reasoning`, oversize arguments) count as no text.
- **From the build:** older decisions have no text in the transaction. `scripts/minutes.mjs` reads `../docs/testnet-run-agent-*decisions.jsonl` (the text exactly, as JSON) and `../docs/testnet-run-agent-*.txt` (the same text behind a `  | ` prefix on each line)
  and writes `dist/minutes.json`, keyed by hash, with the chair's label and kind from the record. It bundles a text only if its SHA-256 equals the hash the record claims; anything else (a missing folder or file, a bad line, a text that does not hash)
  is skipped with a warning and never stops the build. Add a run record to `docs/` under that naming and rebuild to publish its texts.
- **In the browser:** `crypto.subtle.digest("SHA-256", ...)` over the exact UTF-8 bytes of the text, compared with the on-chain hash: verified, mismatch, or not checked (a browser without `crypto.subtle`, which needs https or localhost). A decision with no bundled text shows its hash and
  "reasoning text not published for this decision". The text is shown through `textContent`, with control and bidi characters escaped and said so; the check still runs on the exact text.

A decision with neither a text in its transaction nor a bundled one shows "reasoning text not published for this decision". When both exist, the one that verifies is used.

A match shows the text matches the hash the chair sent, and a text read from the transaction sits in the same transaction as that hash, so it cannot be quietly rewritten afterwards. It does not show the chair was right, that the text caused the rate, or that an AI wrote it: the contract stores only a hash the chair supplies.

## Times the contract told the Chair no

A `set_policy` call the contract turns down changes nothing and logs no event, but the indexer lists the failed transaction. This section (`js/refusals.js`, from `refusalsOfTxs` in `js/decisions.js`) lists every such call, newest first, with the rate it asked for when its arguments can be read, the contract's own panic text taken from the failed receipt (`Smart contract panicked: ...`), and a transaction link. It reads the same transactions as the log, so it shares its trust rules: an index that cannot be read is said, not shown as "no refusals". A refusal by the protocol before the contract runs (for example a wrong method on the chair's restricted key) creates no transaction and so cannot appear.

## Make the Chair overreach

`js/overreach.js` is the game: two big presets (5% a day, -99.99%) or a number of the visitor's own, one button, and a stamp that lands when the contract refuses. It never dead-ends. When the desk answers 429 (a cap, or an address that has used its few an hour) or is closed or unreachable, the panel shows the most recent real refusal from the chain (the stamp, the rate tried, the transaction), says it is an earlier attempt that was not the visitor's, labels who really sent it by the same rules as the refusals section (forced by a visitor through the press desk, a deliberate test call by this project, or just the signer), and says "Try again in N minutes". If the chain's own list of refusals cannot be read at that moment (the index is down), it shows one fixed, documented refusal instead, the project's deliberate +201 bps test (`Efagw855...`, in docs/chair-coin-2/testnet-run-scenario.txt), labelled "an earlier recorded attempt, not yours and not live". The long caveats sit in a fold-out, "How this works, and its limits".

## Your own test coins

`js/mine.js` (with `js/near.js`, which builds and signs the transactions, and `mine.css`) is the panel between the join button and the press conference. It asks the press desk's `GET /health` and `GET /faucet/state`; when the faucet is off, killed, dry, spent or the desk cannot be reached, the panel says so and looks again by itself, and a browser that already holds an account sees it regardless. One button makes an ed25519 key in the browser (WebCrypto, kept in `localStorage`) and posts its public half to `POST /faucet`; the faucet sends the new account 50 test CHAIR and 0.05 NEAR. After that the page signs stake, unstake, claim and send calls itself, with that key, and sends them to the `rpcUrls` nodes (failing over as the page's other reads do). A send that goes through clears the receiver (Send waits for a new one, so a second press cannot repeat the payment); the amount stays, since Stake and Unstake use it too. The panel states that these are test coins from a pool the project controls and that the faucet's 10,000 coins in all are about 1% of the supply. The faucet and its limits are in [`chair-agent/README.md`](../chair-agent/README.md).

## Press conference

`js/press.js` is a panel below the overreach game. The visitor types a question of 1 to 140 characters and presses "Ask the Chair"; the page posts it to the press desk (`POST /ask`, body `{"question"}`) and shows the answer as a quote. A status line then reads "Awaiting entry into the minutes", and becomes "Entered into the record, epoch N" with a transaction link once `GET /record?limit=50` lists a `tx_hash` for that entry. While any of the visitor's own entries is waiting, the page polls every 15 seconds (never longer than 15 minutes for one entry). Below, the public record shows the 10 most recent answers, 3 at first with a "Show N more" button, each with the first characters of its question hash and an epoch link. The record never contains question text, so the page keeps the visitor's own questions in this browser's `localStorage` (key `chair-press-questions`), keyed by entry id, and shows a question only beside the answer it got.

**Finding the desk.** The desk runs behind a Cloudflare quick tunnel whose address (`https://<words>.trycloudflare.com`) changes on every restart, so `pressDiscoveryUrl` in `config.js` points at a small JSON document that a script on the desk's machine rewrites: `{"url": "https://<words>.trycloudflare.com", "updated_at_ms": <number>}`, with `url` empty when the desk has never been up. The page reads it with a cache-busting `?t=<now>`, and uses `url` as the base for `/ask` and `/record`. Both the document and the desk are untrusted: the address is used only if it is exactly an `https` origin under `.trycloudflare.com` with no credentials, port, path, query or fragment (`deskBase` in `js/press.js`); anything else counts as no desk. When a request to the desk does not connect, or the tunnel answers with a server error other than the desk's own 503, the page reads the document once more and retries only if the address changed. While the desk is shut or unreachable the page looks again every 15 seconds (not while the tab is hidden), so the panel comes back by itself; with the desk open and nothing waiting it does not poll. Empty `pressDiscoveryUrl` means no desk: no request is made.

With no desk found, unreachable, or `taking_questions: false`, the panel says "The Chair is not taking questions at this time." with a plain note that the press desk runs on my workstation, and nothing is thrown into the console. The desk must answer cross-origin requests from the page's origin (CORS). Everything it returns is written with `textContent` only, with control and bidi characters escaped like every other chain string.

`test/fake-press.mjs` is a stand-in desk (`node test/fake-press.mjs 18950 [entryDelayMs]`: canned answers, made-up transaction hashes that link to nothing real) that also serves a discovery document at `/chair-press.json`. Because the page accepts only a `trycloudflare.com` address, the tests map a made-up tunnel name onto the stand-in at the fetch boundary, and a browser check can do the same by routing that name to it (Playwright `page.route`).

## Simulation

`site/js/simview.js` runs the repo's own simulator (`../sim`, copied byte for byte into `dist/vendor/sim` by the build; a test checks the copy) in the browser:
The rate is per day, so a 60-epoch run (90 minutes) moves the supply little under any chair; the simulator spreads the daily rate over 960 meetings, as the contract does. The scenarios are `honest-rule-chair` (the shipped `rule-v1`), `chair-goes-silent`, `max-inflation`, `max-deflation`, `max-step-pusher` (swings between the bounds). The assumptions are listed
on the page (staked share, three stakers, 20% velocity, scripted chairs, no price or demand). Every chart has a table view and a legend that also filters.

## What it proves, and what it does not

It shows what the contract has logged and whether those events add up to the contract's own ledger. It does not prove the chair is wise, says nothing about price,
liquidity or returns, and the simulation is a model of supply under stated assumptions, written from SPEC.md and read against the contract source; it does not run the contract.
The event list comes from an index, so it is checked (against the RPC) rather than signed: a difference is shown, never hidden. The fixture is one scripted run of the real
wasm in a local sandbox, recorded once; it is not a deployment and its tokens are not real.

## The rate is per day

`get_params` reports `meetings_per_day` (960 for 90-second epochs); `parseParams` reads it, and the page words every printing rate as "a day" and states the worst case from it (`bound.js`: at most about 2.02% a day at the limit, 1.15 times a week, 1.82 times in 30 days, about 17 months to the supply limit). A token that does not report it is the older per-meeting rule, and the page keeps that rule's per-meeting words and its much faster worst case for it (`printUnit` in `views.js`), so it never describes a contract it is not reading. Burning is always "of every transfer". The overreach and refusals copy is written for the per-day rule.
